# iOS 26 on the Poco F1

This tree is GiaSen's `dipper` branch (Mi 8, same Snapdragon 845) plus the changes for the Poco F1. Bytesfence has already booted iOS 26 with the GPU on a real Poco F1, but the Wi-Fi, Bluetooth, sound, vibration and flashlight work is on the Mi 8. Those are the parts this tree moves over.

**State of this tree:** the kernel and the GPU library both built on GitHub Actions on 2026-11-06, with all three Poco F1 patches applied. Nothing has run on a phone yet.

## What was changed

| File | Why |
| --- | --- |
| `xnu/patches-12377/3100-beryllium-memory-tuning.patch` | Turns on the system cache, DDR and L3 tuning, which was gated to the Mi 8 although it only depends on the chip. `sweetmemtune=0` turns it off. |
| `xnu/patches-12377/3101-beryllium-haptics-torch.patch` | Vibration and flashlight. Limits the motor to 2812 mV: the Mi 8's 3100 mV would overdrive the Poco F1's motor. |
| `xnu/patches-12377/3102-beryllium-audio-board.patch` | Audio DSP and codec clock. Adds the second amp reset pin: the Mi 8's reset pin (gpio76) is the TAS2560's here, and the TAS2559 uses gpio12. |
| `xnu/patches-12377/3104-beryllium-amps.patch` | The player keeps the amps out of reset, so the tuning program stays loaded. It also checks the TAS2560's fault flags and plays the earpiece through the amps. |
| `xnu/patches-12377/3105-beryllium-amp-protects.patch` | `kern.sweet_audio_amp_protects`: the Poco F1's amps protect the speakers themselves, so `SweetSpeaker.driver` drops its power limits and its 12 dB make-up and only holds the peaks under -1 dBFS. |
| `xnu/patches-12377/3106-beryllium-amp-bus-lock.patch` | The bit-banged amp bus gets its own lock. The once-a-second amp check no longer holds the player's lock, which the driver needs on every cycle, so iOS no longer skips ahead (the crackle at full volume). |
| `xnu/patches-12377/3107-beryllium-amp-wake-lock.patch` | The same for the amp's sleep and wake scripts: the first sound after 5 s of silence no longer loses its start. |
| `xnu/patches-12377/3108-beryllium-volume-down-pull-up.patch` | Reads the volume-down key's pull-up (PM8998 PON_PULL_CTL) at start and switches it on if it's off, as Android does. On this phone it was already on (0x0f), so nothing is written: kern.sweet_keys_pon_pull shows the value. |
| `tools/audio/tas2559fw.py` | Makes the I2C scripts for both amps from the phone's firmware and calibration. The scripts hold TI's firmware, so they stay on the phone. |
| `xnu/patches-12377/0020-stage-bearssl.sh`, `xnu/vendor/sweet_bearssl-7bea48e` | From ferdza's fork. On GitHub Actions the kernel build no longer fails when bearssl.org is down. Other hosts need `GITHUB_WORKSPACE` set to the tree. |
| `.github/workflows/chlorophyll.yml` | Builds the GPU library on a macOS runner. Adapted from ferdza's fork. |
| `.github/workflows/xnu.yml` | Defaults to macOS 26.5 sources. The steps that package Apple SDK headers and closed-library symbol lists are off, so a public fork doesn't publish them. |
| `tools/beryllium-mkboot.sh` | Makes boot images in steps, adding one hardware block per level. |

| Flashlight | PMI8998 | PMI8998, both LEDs rear | Patched |

## Build order

1. **Kernel:** run the `xnu.yml` workflow from the fork's default branch, about 20 minutes. A workflow can only be started by hand if it exists on the default branch, so make `poco-f1` the default before the first run.
2. **GPU library:** run the `chlorophyll.yml` workflow.
3. **Device tree (ADT):**

   ```bash
   python3 tools/mkadt.py enxerto/out/beryllium-n104-2x.adt --board beryllium --highmem --identity n104ap --display-scale 2 --points 414x896
   ```

   Then add Wi-Fi and the GPU firmware with `tools/adt-wlan.py` and `tools/adt-gpufw.py`. Name the result `enxerto/out/beryllium-n104-2x-wlan-gpu-hap.adt`.

4. **iOS root:** Mac, or Linux as root. The GPU step calls `otool` and `install_name_tool`, so a Linux host needs cctools as well.

   ```bash
   RENEGADE_BT_FW=DIR SWEET_QUIET=1 RENEGADE_CHL=1 RENEGADE_CHL_DIR=DIR/usr/local/lib/bgmtl tools/renegade/renegade update ROOT.simg --no-jb
   ```

   Leave `RENEGADE_AMP_FW` unset: it generates the Mi 8's single-amp scripts, which are wrong for this phone.

5. **Boot image:**

   ```bash
   LEVEL=1 tools/beryllium-mkboot.sh KERNEL OUT.img
   ```

Change one level per boot and keep the log of each. `fastboot boot OUT.img` runs from RAM, so a bad image is gone after a restart.

| Level | Adds | Good result |
| --- | --- | --- |
| 1 | Display, touch, USB, battery | Home screen with CPU drawing, SSH over USB |
| 2 | Wi-Fi | Joins a WPA2 network |
| 3 | GPU | Home screen on the GPU. The first boot can look stuck while shaders compile |
| 4 | Bluetooth | Stays up next to Wi-Fi, then try pairing |
| 5 | Vibration, flashlight | Both work; the log shows the 2812 mV limit |
| 6 | Audio probe | Reads only; the log shows both amp reset pins |
| 7 | Audio DSP | DSP runs. The boot job loads the amps about 3 minutes after the start, and `sweetplay` plays a raw PCM file |

## Lessons from Bytesfence's real Poco F1

- `touch /usr/local/share/launchd-disable-memory-limits` and a reboot stopped thousands of memory kills.
- A zero-byte `/private/var/tmp/bgmtl.notrim` keeps the GPU's memory trimming off.
- Every executable copied in by hand needs `chmod 755`.
- Missing GPU firmware causes a spin of about 600 seconds, which is easy to mistake for a dead boot.
- A separate `win` partition keeps Android's data. Boot it with `ROOTPART=win`.
- TWRP in recovery plus `tools/hfs-cat-surgery.py` rescued a boot loop.

## Still to do with the phone

- Starting without the PC (2026-11-08): the level 7 image (Enxerto with kernel 3114, sha256 18fde946ce5f2d02...) is written to the `boot` partition with ABL's `fastboot flash boot` (partition size 0x3FFC000, image 22 MB; Sending OKAY 0.5 s, Writing OKAY 0.1 s). `fastboot reboot` then started it from the partition: the USB network appeared after 8 s, the amps were up after 162 s, 0 panics, 0 RPMh timeouts, DSP and codec up, the jack detector on, Wi-Fi joined, charging as on RAM boots. Enxerto powers USB up on every start (`usb_power_up`), so SSH works after a cold start too. The phone's earlier `boot` (crDroid's) is kept off the repository; without it a normal power-on started Android, which can't read the HFS data and offers a factory reset. Power off was missing in 3114: `SweetPlatformExpert::haltRestart` handled only restarts and panics, so iOS's "slide to power off" (`kPEHaltCPU`) ended in the stock spin with the phone still on and the screen black (the user saw exactly that).
- Power off (3115, RAM-tested 2026-11-08, not in the `boot` partition yet): `kPEHaltCPU` -> `sweet_reboot_poweroff()`: UFS flush, the stored reboot reason cleared, PSCI SYSTEM_OFF, and if the firmware returns, the PM8998 PS_HOLD reset type set to shutdown (0x85a = 4, 0x85b reset enable off for 500 us around it, as qpnp-power-on.c) and PS_HOLD low. `sweetreboot poweroff` (sysctl mode "poweroff" + `reboot(RB_HALT)`) refuses kernels without 3115. Result: USB gone after 8 s, nothing back; with the cable in, the PMIC started the phone again in ABL's charger path, so Enxerto's charging screen ran on hardware for the first time (holding Power 2 s started iOS). A restart after that still lands in fastboot (the reset type does not stay "shutdown"). The UDP log ends at `unmount(0) /`, so which of the two paths powered off is not known.
- Screen when the phone sleeps (3116, RAM-tested): it went very dim, not dark. `blSet(false)` wrote WLED brightness 0 but left the PMI8998 WLED module on (MOD_EN 0xd846 bit 7, as ABL set it), and brightness 0 with the module on still lights the strings faintly. qcom-wled.c switches the module off at 0; now off = brightness 0, then MOD_EN 0x00, and on = the brightness, then MOD_EN 0x80, read back each time (log: `backlight off (0x0000/0x0000, MOD_EN 0x00)`, `backlight on (0x07ff/0x07ff, MOD_EN 0x80)`). Enxerto's charging screen had the same fault in its 20 s idle blank and got the same fix (`pmic_wled_module`).
- Starting asleep (3117, RAM-tested): after every boot SpringBoard started with `cbDisplayMode:Off` and waited 9 s for CoreBrightness, because the Poco F1 had no `AppleARMBacklight` service (`backlight-control -> none`; it was left off since 0246/0249). It now has one, with its own panel data: EBBG FT8716 / Tianma NT36672A LCD, 420 nits peak (`qcom,mdss-dsi-panel-peak-brightness` 4200000 in both panels' nodes), PMI8998 WLED 20 mA full scale per string, mid 7 mA = 147 nits, minimum 2. Result: `startup cbDisplayMode:ActiveOn`, the lock screen comes up lit after boot and turns off by itself like an iPhone's, backboardd stable, CoreBrightness drives the WLED (`brightness-nits-cap` 420, then its ramps). CoreBrightness' slider is logarithmic: L = 2 x 210^slider nits. Side effects: the stored brightness (SpringBoard's `SBBacklightLevel2` 0.19, CoreBrightness slider 0.35) is 13 nits until the slider is moved, and True Tone ("Harmony") is on with a fixed warm white point (no light sensor: pushed white point x 0.339, y 0.350). Home-screen swipes: 54-57 fps rendered, 50-54 shown (3116: 53-56 and 52-55), swap to scan-out median 14-16 ms (was 7-8). 3118 stops the one log line per brightness step.
- No sound on the 3117/3118 kernels (found 2026-11-08, fixed in 3119): every boot of both had `cx.lvl ARC vote failed errno=60` and `SWEET AUDIO: cx vote failed`, so the audio DSP never started. Not the backlight service: 3118 with the service off (`sweetfb_blsvc=0`) failed the same way, and 3116 with the new Enxerto worked. The cause is a race in `rh_cmds` (sweet_rpmh.c). It accepted a finished request only after seeing the TCS's IRQ bit (masked for our TCS, so always 0) or a busy/incomplete state after the trigger, to rule out stale CMD_STATUS. A vote that changes nothing (CX already at that level) finishes before the first poll: idle 0x1, CMD_STATUS 0x10101 (ISSUED|COMPLETE), CONTROL 0x1010000 (AMC_EN|TRIGGER) from the first read on. After 100 ms it was taken for a timeout, the TCS quarantined and RPMh refused for the rest of the boot. Older kernels had it now and then: 4 of the 37 older boot logs with RPMh lines (the audio DSP's cx vote, once Wi-Fi's ldoa17 enable). All 4 boots of the 3117/3118 kernels had it, so their code layout makes the first poll late enough every time. 3119 counts a request as done when it stays idle with every command complete, unchanged, for 1 ms after the trigger and CONTROL still reads AMC_EN|TRIGGER (logged as `finished before the first poll ... accepted`, first 4 per boot). A busy TCS or an incomplete command still times out as before. Tested 2026-11-08/09 on three RAM boots: on boots 2 and 3 the audio DSP's `cx.lvl` vote (hlvl 7) finished before the first poll, 3119 accepted it, and the DSP answered (`audio framework ready`). Boot 1 didn't hit the race (every request showed progress). All three: 0 RPMh timeouts, amps up after 171-181 s, Wi-Fi joined, `startup cbDisplayMode:ActiveOn`, 0 panics. Power press: `backlight on (..., MOD_EN 0x80)`, then off by itself with MOD_EN 0x00. Home-screen swipes: 52-56 fps shown, swap to scan-out median 5-7 ms (3117: 14-16). On boot 1 the USB network stalled from the start (the phone's TX queue full at 32 frames, Debian's vhci reported resets) while iOS itself ran fine on Wi-Fi. It was reached over SSH at its Wi-Fi address, and boots 2 and 3 had working USB, so this was a one-off link fault.
- 3120 (2026-11-09) is 3119 without the temporary `finished before the first poll` log line. One RAM boot: 0 RPMh timeouts, DSP answered, Wi-Fi joined, `startup cbDisplayMode:ActiveOn`, 0 panics.
- Audio start time (2026-11-09): with the driver's default `sweetaudiodelay` the audio DSP starts 150 s after the root mount, so iOS had no sound for about 2.5 minutes after every boot. The wait exists because the DSP's firmware reads and Wi-Fi's share one FAT reader in beryllium_wlan.c (one `wl_fatbuf`, one `wl_dirbuf`), and only audio's side (`sweet_modem_file` under `sweet_share_lock`) is locked. The other users are `wl_probe` and the Bluetooth firmware at about 5 s, and the modem bring-up for Wi-Fi at `sweetwlandelay=60` (mba.mbn, modem.mdt, bdwlan, the modem's TFTP reads). Audio's reads take about 7 s, so `sweetaudiodelay=30` puts them in the idle gap. `tools/beryllium-mkboot.sh` LEVEL 7 now adds it. Tested from RAM and from the `boot` partition: the DSP answered 26 s after SpringBoard's start (it was about 150 s), the MSS bring-up began 24 s after the DSP was ready, Wi-Fi joined, the Bluetooth firmware loaded (FIFO errors 0), 0 RPMh timeouts, 0 panics. - Checked by hand on the flashed image (2026-11-09, the user: "all good"): the sleeping screen is dark (3116), sound plays soon after a restart, "slide to power off" switches the phone off (3115), and Enxerto's charging screen goes black after 20 s and comes back with Power. Still seen: after a start the screen goes off by itself within a few seconds, although SpringBoard logs `startup cbDisplayMode:ActiveOn` since 3117. Cause, from SpringBoard's own log: the lock screen's idle timer. At the end of its start-up SpringBoard applies `SBIdleTimerDescriptor ... total: 6.0s reason:"Startup"` (duration Default; Auto-Lock does not apply on the lock screen), then `attention event: expire @ 6`, `ScreenSleepCoordinator: beginning sleep for source IdleTimer`, and the kernel gets backlight off 0.3 s later. The attention clients (`AWAttentionAwarenessConfiguration`) fail with `Socket is not connected`: there is no Face ID attention sensor, so nothing extends the 6 s. The display goes off at the same point on 3114, 3119 and 3120 (23-24 s after the kernel's `display on`), so it is iOS's normal untouched-lock-screen behaviour, not a kernel fault.

PowerState:1 managerState:5`; the kernel sets BD_ADDR 02:00:5e:77:b0:01 (the ADT's `local-mac-address`) over the firmware's 39:90:21:74:07:00 with QCA's 0xfc14 and reads it back; keychain queries answer -25300 (nothing stored), not an access error. `Unable to turn on BT)_WAKE signal (status=65535)` every ~15 s is the missing `/dev/btwake`, harmless. - Scrolling smoothness (2026-11-09, no kernel change): measured with `poco-scenes.py`, a Poco copy of `tools/dipper-scenes.py` (18 test-finger scenes over `kern.sweet_touch_drag` and `sweetopen`, no screenshots), and a per-frame breakdown of `kern.sweet_fb_trace` (gap, swap to scan, SwapWait) plus `kern.sweet_gpu` level residency. After a pause the GPU sits at a low level, the input floor (`a630_input_level`, default L4 = 520 MHz) held it there on a touch, and the governor (100 ms windows) took about 300 ms to reach L7. In that time a scroll's frames came 10-37 ms apart: at the start of a Safari scroll the GPU spent 340 ms below L7. `sweetgpuinput=7` (now in the LEVEL 3 line of `tools/beryllium-mkboot.sh`) makes the touch floor L7. - Zero-copy scan-out (2026-11-09, RAM boots only, not adopted). `sweetfb_direct=1 sweetfb_scancopy=2` without `sweetfb_zcforce`: `smmu=translate-or-unknown`, `mode=copy` (the safe outcome). A read-only probe of both MDP streams through `kern.sweet_audio_smmu` (writes 0x880 / 0xc80 run `sweet_smmu_probe_sid(sid, 2)`): sCR0 0x270406 (CLIENTPD 0, USFCFG 1), 76 SMRs, 45 CBs; SMR 0 0x80080880 and SMR 1 0x80080c80 (mask 8) -> S2CR 0x0 = TRANSLATE to context bank 0; CB 0: CBAR 0x10003 (stage 1, stage 2 bypass, VMID 3), **SCTLR 0xe0 (M = 0, translation off; CFRE/CFIE/CFCFG set)**, TTBR0 0, TCR 0, MAIR0 0, FSR 0x400 (format field only, no fault). So ABL leaves the display streams on a disabled bank: IOVA = PA, effectively bypass. The probe classifies by S2CR type only, hence "translate"; it could also read SCTLR.M. With `sweetfb_zcforce=1` added (room in the 607-byte field: `sweetfb_hw=1`, `sweetfb_flip=1`, `sweetfb_scale=1` are implied by direct mode on this canvas, and `sweetfb_vsync=1` does nothing at 60 Hz): `mode=direct`, 5122 of 5130 frames scanned through the GPU blit (`scan_gpu_copies`, 0 fallbacks, 0 submit fails), 0 panics, 0 SMMU faults, no reset. Rounds 2-3, shown fps: Safari flick 60 -> 48-58, flick back 60 -> 49-52, Settings open 34-43 -> 29-38, Spotlight 46-52 -> 34-44, app close 41-42 -> 31-40, Settings scrolls about the same. The per-frame blit lands on the GPU, the part that already runs out of time, while the CPU copy it replaces costs 1.3 ms on average. Kept off.

Not a problem: DDR and L3 already drop with the display off (3026), the GPU sleeps after 30 s, the AMP spin is capped at 200 us, panel sleep gave nothing on the Mi 8.

- Headphone jack (2026-11-08: detection, the kernel's playback and the iOS device work; the headset mic is still to do):
  - **iOS side.** VirtualAudio, the plug-in iOS's audio server routes with (`/Library/Audio/Plug-Ins/HAL/VirtualAudio.plugin`, a separate 7.3 MB file, not in the dyld cache), still has the wired-headphone code of the iPhones that had a jack. A "Codec" device class (`Device_Codec_Aspen`) makes "wired-headphones", "wired-microphone" and "line-out" ports from the routing database's port list. A jack handler (`HALJackStateHandler`) listens to `kAudioDevicePropertyJackIsConnected` on the device's input and output. A USB path makes "USB headphones" output and "USB headset" input ports. The iPhone 11 has no jack, so its routing for "Codec" has no wired entries; the USB path is what Lightning headphones use, so the driver's headphone device says it is USB.
  - **iOS device: works (3113 + SweetSpeaker.driver, 2026-11-08).** How VirtualAudio's `DeviceFactory` sorts HAL devices (its disassembly; the factory sits in `HALDeviceManager`): first by UID (Codec, Baseband Voice, USB Audio Output, USB IDAM, Speaker, ... Receiver), then, after "Unhandled UID", by transport type (`airp`, `blue`, `usb `, `dprt`, `hdmi`, `null`, `thun`, `pci `, `ccwd`, `ccwl`, `cscr` and a few more). `usb ` makes a `Device_USB_Aspen`, whose constructor first reads the custom property `lcID` (the USB location ID, a CFNumber) and gives up without it (audiomxd: "CAException caught by ExceptionBarrier: 'who?'"). The HAL passes a driver only the custom properties the device lists in `kAudioObjectPropertyCustomPropertyInfoList` (`cust`), so the device lists `lcID` as a property list and answers a number. Then VirtualAudio makes a USB output port (`puso`) and a tap port, and the route goes "Speaker -> USB~SweetHeadphones~" with reason NewPortConnected. It is a plain USB port, not a headphones one: ADAM registers only USB-C accessories ("Registration is only for USBC devices"), so the class logs "Not registered with ADAM as headphones" and "Forcing USB Default sub type". The device: UID "SweetHeadphones", 2 channels, its own volume (-48 to 0 dB) and mute, in the device list only while `kern.sweet_jack` bits 0 and 1 are set (a thread polls twice a second) or while `/private/var/tmp/sweethp.on` exists (a test switch audiomxd can see). Its IO starts the kernel player with `PL_OP_START_HPH` (8, 3113: the headphone path comes up first if needed); its IO end and an unplug send `PL_OP_HPH_OFF` (9). Silent check (codec at its quietest step and muted, the test switch, `phone-hp-test.sh`): iOS's silence went to the headphone device at iOS volume 0.30, the kernel brought the path up ("headphones on (player)", both PA ramps done, no over-current), and after the switch was removed the IO stopped, the path went down and the next playback was on the speaker. The user's test with AKG K612 Pro (62 ohm): iOS played on them; unplugging paused playback, as on an iPhone; iOS keeps a separate volume for the headphones and the speaker. At full volume it was only just loud enough, so 3114 makes Xiaomi's level the default (digital -1 dB instead of -20 dB; full iOS volume = Android's full volume). Restarting audiomxd alone loads a new driver: the phone has no `launchctl` or `killall`, so `phone-amx-restart.sh` takes audiomxd's pid from its log lines and kills it, and launchd starts it again.
  - **Plug detection: works (3111, 2026-11-08).** The WCD9340's jack detector (MBHC). Its interrupt pin goes to TLMM 54 (`wcd9xxx-irq`). Insertion and removal are codec interrupt 8 (`MBHC_SW_DET`): status 0x0411-0x0414, mask 0x0409, clear 0x0419. The device tree sets the jack's left-channel and ground switches as normally open (`hphl-swh` 1, `gnd-swh` 1). First tried by hand with `sweetreg` (`phone-jack-arm.sh`, `phone-jack-watch.sh`): plugging in and out gave one interrupt each, and ANA_MBHC_RESULT_3 bit 4 (SWCH_LEVEL_REMOVE) reads 1 with nothing in the jack and 0 with a plug. Patch 3111 does it in the kernel: a "sweet jack" thread brings the codec up 20 s after the DSP, arms the detector the way Linux's `wcd_mbhc_initialise` does, polls the status twice a second, takes the state from the switch level at each interrupt and arms the other edge, and checks every 10 s that the detector is still on. `kern.sweet_jack`: bit 0 plugged in, bit 1 detector on, bits 8 and up the number of changes. On the phone: "SWEET JACK: detector on, nothing plugged in", then "plugged in" and "unplugged" for a real plug, `kern.sweet_jack` = 514 (2 changes, detector on); the mic and speaker levels did not change. Headphones and headsets are not told apart yet (that needs MIC BIAS2 and the MBHC ADC).
